# gh-pr-schema

## タイトル

変更目的を一文にしたものをタイトルにする。

- 本文には書かない

## 文書構成

次の順で出す。並べ替えと追加をしない。

```markdown
## 変更目的

- [変更目的]

## 変更内容

- [冒頭]

### 処理フロー

[処理フロー]

### [トピック見出し]

- [トピック]

## テスト内容

- [テスト内容]

## 関連 Issue

[関連 Issue]
```

### 変更目的

なぜこの変更が必要かを書く。

- diff から推測しない
- `## 変更内容` の列挙にしない

### 変更内容

差分で何がどう変わったかを書く。

#### 冒頭

変更の全体像を、`## 変更内容` の直下に見出しなしで書く。

```markdown
- [何を変えたか]
- [レビューで押さえるべき点]
- [前提・注意]
```

- レビューで押さえるべき点と前提・注意は、誤解や事故につながるときだけ書く
- トピック見出しの言い換えだけにしない

#### 処理フロー

コンポーネント間のやり取りの順を図示する。

````markdown
### 処理フロー

```mermaid
sequenceDiagram
```

- [補足]
````

- シーケンス図に限る。複数置いてよい
- 補足は、図に表せない前提や制約だけ書く。図の言い直しは書かない。不要なら補足を省く
- 1 コンポーネントで完結するときは、見出しごと省く

#### トピック見出し

差分をテーマごとに書く。1 つ以上置く。

```markdown
### [トピック見出し]

- [そのトピックで何がどう変わったか]
- 関連コード:
  - path/to/file.ext:開始行-終了行
```

- 見出しは diff から付ける。変化が伝わる名前にする
- ファイル名の羅列にしない
- 関連コードは、そのトピックの主要な変更箇所だけ書く。不要なら省く
- リポジトリ URL が分かれば、リンク先は GitHub の blob 形式にする。分からなければパスだけ書く

### テスト内容

どこまで検証済みかを書く。

```markdown
- [テスト内容]
```

- diff にあるテストの追加・変更から書く
- テストの変更が無ければ `- なし`

### 関連 Issue

この PR と Issue の関係を、本文の末尾に書く。

```markdown
Closes #10
Related: #20
```

- プレーンテキストで置く。バッククォート、コードブロック、引用には入れない
- `Closes` はこの PR で完了する Issue。デフォルトブランチへのマージで GitHub が閉じる
- `Related:` は言及するが閉じない Issue。マージしても開いたまま
- 同じリポジトリの `Closes` は `Closes #10`。別リポジトリは `Closes owner/repo#10`
- `Closes` が複数あるときは行を分ける。各行にキーワードを書く。`Closes #10, #123` とは書かない
- ベースがデフォルトブランチでないときは `Closes` を書かない
- 書く行が無ければ、見出しごと省く
