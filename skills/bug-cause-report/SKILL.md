# bug-cause-report

## できること

- 観測された不具合が、今のコードのどこで・なぜ起きるかを調査する
- `原因特定` / `有力候補` / `特定不可` / `要確認` を判定する
- 変える箇所が見えているときは、原因の説明に直し方の案内を添えてよい
- 結果を日本語 Markdown として `bug-cause-report.md` に保存する

## いつ使うか

- バグの原因
- なぜこの不具合が起きるか
- どこで起きているか調べて
- 原因をレポートして

## 実行手順

### 1. 観測された不具合を確認する

観測は必須。調査の前にヒアリングする。確認した内容はレポートの `## 調査目的` にし、`# {タイトル}` はその端的な表現にする。

「何がおかしいか」を短く書いてもらう。エラー、再現手順、チケットの貼り付けでもよい。

観測が曖昧なまま調査に入らない。

### 2. コードベースを調査する

レポートを書く前に、既存コードを一次情報として調査する。調査するまでレポートは生成しない。

- 症状に対応する処理経路、分岐、状態の持ち方を探す
- 関連コードに使えるパスと行番号、判定に効く根拠を残す
- 見つからないことは「ない」と断定せず、見つからなかったと書く
- 貼られたログやエラーは手がかりにし、コードで確かめる
- 必要に応じて `AGENTS.md`、周辺コード、既存テスト、設計資料を読む
- 対象リポジトリのローカル規約を優先する

観測とコードが矛盾した場合は、自動解決せず確認する。

### 3. 結果を組み立てる

このステップの前に `references/report-schema.md` でレポートの型を確認する。書き方は `report-patterns` に従う。

### 4. 保存して返す

手順 3 の本文をワークスペースルートの `bug-cause-report.md` に書き出す。

既存の `bug-cause-report.md` があれば上書きする。保存後、保存先パスと本文をチャットへ 1 回だけ返す。

## 禁止事項

- `references/report-schema.md` を読まずに出力しない
- コードを調査する前にレポートを生成しない
- 調査していない事実を断定しない
- 見つからないことを「存在しない」と言い切らない
- ヒアリングしていない観測を推測で埋めない
- パッチ、PoC、実装手順を書かない
- 判定に修正方針を混ぜない
