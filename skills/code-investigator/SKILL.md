# Code Investigator

既存コードを調査し、原因・影響範囲・対応方針を明らかにする調査スキル。
調査の手順やツール選定は状況に応じて最適化してよいが、最終出力は「レポート要件」を必ず満たすこと。

## 実行開始時に最初に確定する項目

1. 調査目的（何を判断するための調査か）
2. 調査範囲（対象機能、対象モジュール、除外範囲）
3. 調査読者（実装者、レビュアー、意思決定者）
4. 完了条件（何が分かれば調査完了か）

不足情報がある場合は、仮置きせず確認質問を返す。

## レポート要件

レポートは読者が次アクションを判断できる、意思決定可能なものであること。具体的には以下をすべて満たす。

- 先頭に結論サマリを置く。結論・根拠・推奨アクションを3点以内で示し、読者が1分で状況を把握できる密度にする
- 主要主張ごとに最低1つのコード根拠を付ける。根拠は「リポジトリ相対パス + シンボル名」で示し、可能な限り行番号も併記する
- 推測と事実を混ぜない。観測事実と解釈を分けて書く
- 影響範囲を直接影響（壊れる・変わる箇所）と間接影響（依存先、周辺フロー、運用）に分ける
- 未調査領域（今回見ていない範囲）を明示する
- 対応方針を優先順位付き（最優先・次点・見送りと理由）で示し、高リスク項目には「リスク:」を付記する
- 次アクションは担当者目線で実行可能な粒度にする

## レポートテンプレート

以下の構造を維持する。論点の数は調査内容に応じて増減してよい。

```markdown
# 目的
- 背景:
- 判断したいこと:
- 調査範囲:
- 非対象:

# 結論サマリ
- 結論:
- 根拠:（3点以内）
- 推奨アクション:

# 調査詳細
## 論点: <論点名>
- 観測事実:
- コード根拠: （リポジトリ相対パス, 関数/クラス名, 行番号）
- 補助根拠（ログ/クエリ/設定）:
- 解釈:

# 影響範囲
- 直接影響:
- 間接影響:
- 未調査:
- 注意点:

# 対応方針
- 最優先:
- 次点:
- 見送りと理由:
```
