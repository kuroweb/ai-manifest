# feature-research

## できること

- ヒアリングした画面か機能 1 つについて、現行の構成と処理の流れを調べる
- 結果を日本語 Markdown として保存し、チャットには保存先と概要だけを返す

## いつ使うか

- `feature-research`
- `feature-research --output docs/order-detail.md`
- スキル名が無いときは使わない

## 実行手順

### 1. 対象を確認する

調べたい画面か機能と、何のために調べるかを、ユーザーにヒアリングする。ユーザーの言葉のまま受け取る（例: 「注文詳細」「注文詳細のキャンセル」、「改修の前に今の作りを知るため」）。

### 2. 対象を特定する

カレントディレクトリのリポジトリを起点にする。ユーザーがパスを示したときは、そのパスを起点にする。起点の `AGENTS.md` を読み、その規約に従う。

手順 1 の対象の入口（URL、API、コマンド、ジョブなど）と、それを処理するコードを特定する。機能を聞いたときは、その機能が載っている画面と、機能を担う処理や API を特定する。候補が複数あれば、見つけた候補を示して、対象に含めるものをユーザーに選んでもらう。

### 3. 調べる

特定した対象を構成する要素を調べる。要素ごとに、所在をパスと行番号で残す。

コードや `AGENTS.md` が別のリポジトリを指していたら、そのリポジトリも読み、その `AGENTS.md` に従う。場所は次の順で決める。候補が複数あれば、パスと `.git/HEAD` のブランチを示して、ユーザーに選んでもらう。

1. ユーザーが示したパス
2. 起点の親ディレクトリの直下にある同名のディレクトリ
3. ユーザーに聞く

調べる中で見つけた挙動（表示の分岐、権限、エラー時、副作用）は全て残す。テストがあれば、挙動の根拠に足す。

画面上の操作（ボタン、リンク、フォーム）と、対象への入口は、対象を使う利用環境ごとに洗い出す。ユースケース詳細は、ここで洗い出したものから描く。

対象が読み書きするテーブルと列を、コードから洗い出す。スキーマ定義があれば、それで確かめる。

見つからないものは「無い」と断定せず、見つからなかったと書く。

### 4. 資料で補う

使える MCP やユーザーが示した資料で、手順 2 で特定した対象の名前と入口を検索する。使えるものが無いときは、この手順を飛ばし、飛ばしたことをユーザーに伝える。

一次情報はコードとし、資料はコードで分からないことを補うために使う。

- 業務ルールの目的が資料に書かれていれば、それを目的にし、根拠にその資料を足す
- 手順 3 で確かめられなかったことが資料で確かめられれば、本文に入れ、未確認事項から外す
- 資料とコードが食い違うときは、コードを事実として書き、食い違いを未確認事項に入れる

### 5. 現状調査にまとめる

`references/research-schema.md` の型で書く。

### 6. 保存する

slug は、手順 2 で特定した対象を表す kebab-case にする（例: 注文詳細なら `order-detail`）。

保存先は次の順で決める。同じパスにファイルがあれば上書きする。

1. `--output` で指定されたパス
2. ワークスペースルートの `feature-research-[slug].md`

保存後、チャットには保存先パス、概要を 2〜3 文、未確認事項の件数だけを返す。本文はチャットに貼らない。図と表が TUI では読めないため。

## 禁止事項

- `references/research-schema.md` を読まずに書かない
- 調べていない事実を断定しない
- 改修方針や対応方法を決めない
