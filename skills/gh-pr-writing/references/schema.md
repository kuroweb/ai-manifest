# GitHub Pull Requestの型

## タイトル

変更目的を一文で書く。

## 文書構成

見出しは次の順で出す。`### 処理フロー` 以外の見出しは省かず、書くことが無ければ `- なし` と書く。

```markdown
## 変更目的

- [変更目的]

## 変更概要

- [変更概要]

## 変更詳細

### 処理フロー

[処理フロー]

### [トピック見出し]

[トピック]

## テスト内容

- [テスト内容]

## レビュー観点

- [レビュー観点]

## 関連チケット

[関連チケット]

## 関連 Issue

[関連 Issue]
```

### 変更目的

なぜこの変更が必要かを書く。課題と、それをどう解決するかを書く。

### 変更概要

変更の全体像を 1〜2 項目で書く。個々のトピックは列挙しない。

### 変更詳細

差分で何がどう変わったかを、処理フローとトピック見出しで書く。

#### 処理フロー

変更がまたがるコンポーネント間のやり取りを、mermaid の図で 1 つ示す。

````markdown
```mermaid
sequenceDiagram
```

- [補足]
````

- やり取りが主ならシーケンス図、分岐や状態遷移が主ならフローチャートにする
- コンポーネントは、変更の判断を担うファイル（リポジトリルートからのパス）、外部サービス、永続ストアにする
- 主要な経路だけを描き、例外やエラー処理は補足に書く
- 省略条件: 差分が 1 ファイルで閉じるとき、またはドキュメント、設定、rename、テストだけの変更のとき

#### トピック見出し

差分をテーマごとに、何がどう変わったかと、その振る舞いを決める関連コードを書く。1 つ以上置く。

```markdown
### [トピック見出し]

[そのトピックで何がどう変わったか]

- [path/to/file.ext:開始行-終了行](リンク先)
```

- 同じ変更が複数のモジュールに並ぶときは 1 つの見出しにまとめ、関連コードは代表の 1 つにする
- 関連コードは、変更を含む関数や型、またはブロックの範囲を、head の最新コミットの blob リンクで示す

### テスト内容

変更した振る舞いのうち、head の最新コミットで確かめたものを 1 行に 1 つ、`〜こと` で書く。確かめ方は子の箇条に書く。

```markdown
- [確かめた振る舞い]こと
  - [テストファイルとテスト名、または実行したコマンド]
- [確かめた振る舞い]こと
  1. [手で行った操作]
  2. [見た結果]
```

### レビュー観点

レビュアーに確かめてほしいことを、1 行に 1 つ、`〜か` の問いで書く。

```markdown
- [状況や判断]が、[確かめてほしいこと]か
```

- 重点的に見てほしい箇所
- 確信が持てない箇所
- 選んだ判断
- 確かめていない振る舞いや、失敗したまま残る検査（確かめていない理由を添える）

### 関連チケット

この PR に対応する、GitHub の外にあるチケットの URL、または分からなければ ID をプレーンテキストで書く。

### 関連 Issue

この PR で完了する Issue を、本文の末尾に `Closes #<番号>` とプレーンテキストで書く。
