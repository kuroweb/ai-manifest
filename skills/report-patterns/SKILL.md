# report-patterns

## できること

- レポート、PR・MR本文、引き継ぎノートで使う記述パターンを示す
- 書いた本文が、記述パターンで読みやすくできるかを確かめる

## いつ使うか

- 他のスキルが`report-patterns`を読むよう指示したとき
- ユーザーが`report-patterns`と明示したとき

## 記述パターン

### 見出し

見出しだけで、その節が何のための記述か分かるようにする。

```markdown
### [目的や概要が伝わる見出し]
```

- 名詞だけのラベル（「返り値」「境界」「利用」など）にせず、目的や概要が伝わる言い方にする
- 同じ種類の論点を並べる節では、目次や見出し一覧を流し読みしただけで概要が掴めることを優先する
- 悪い例: `### [名詞だけのラベル]`

### コードリンク

コードをリンクするときに使う。

```markdown
[リンクテキスト](リンク先)
```

- `[リンクテキスト]` は `path/to/file.ext:開始行-終了行`
- クラスやファイル全体のときは、行番号を省略してよい
- `[リンク先]` は GitHub / GitLab の blob 形式
- リポジトリ URL が分からなければ、リンクにせず `path/to/file.ext:開始行-終了行` だけ書く

### 関連コード

コードを根拠にするときに使う。ラベリングは、直前の文脈だけではリストの役割が分かりにくいときや、同じレポート内で複数のリストを区別したいときに書く。

```markdown
[ラベリング]

- path/to/file.ext:開始行-終了行
- path/to/file.ext:開始行-終了行
```

- `[ラベリング]` は `関連コード:` または `（短い修飾）の関連コード:`

### 実行フロー

実装がどの経路を順に通るかを書くときに使う。ラベリングは、直前の文脈だけではリストの役割が分かりにくいときや、同じレポート内で複数のフローを区別したいときに書く。

```markdown
[ラベリング]

- path/to/file.ext:開始行-終了行
  - [このステップで何をするか]
- path/to/file.ext:開始行-終了行
  - [このステップで何をするか]
```

- `[ラベリング]` は `実行フロー:` または `（短い修飾）の実行フロー:`

### 既存例

説明のあとに、リポジトリ内の代表実装を示すときに使う。ラベリングは、直前の文脈だけではリストの役割が分かりにくいときや、同じレポート内で複数のリストを区別したいときに書く。

```markdown
[ラベリング]

- path/to/file.ext:開始行-終了行
  - [何が既にあり、どう対応するか]
- path/to/file.ext:開始行-終了行
  - [何が既にあり、どう対応するか]
```

- `[ラベリング]` は `既存例:` または `（短い修飾）の既存例:`

### テーブル

表にするときに使う。

```markdown
| [列] | [列] |
| --- | --- |
| [セル] | [セル] |
```

- 区切り行の `-` は `---` で足りる。列幅に合わせて伸ばさない

### シーケンス図

処理の流れを示すときに使う。

````markdown
```mermaid
sequenceDiagram
```

- [補足]
````

- 複数置いてよい
- `participant` を増やしすぎない
- `[補足]` には図に表せない前提や制約を書く。図の内容を言い直さない。不要なら省略する

## スキル連携

| ユーザーの依頼 | ワークフロー |
| --- | --- |
| 不具合の原因を調べる | `report-bug-cause` → `report-patterns` |
| 実装できるかを調べる | `report-can-implement` → `report-patterns` |
| それ以外の問いを調べる | `report-question` → `report-patterns` |
| PRのタイトルと本文を書く | `gh-pr-writing` → `report-patterns` |
| MRのタイトルと本文を書く | `glab-mr-writing` → `report-patterns` |
| 引き継ぎノートを作成 | `handover-create` → `report-patterns` |
