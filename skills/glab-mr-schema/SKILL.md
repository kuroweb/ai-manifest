# glab-mr-schema

## タイトル

変更目的を一文にしたものをタイトルにする。

- Conventional Commits の type と scope は付けず、MR 全体の目的が伝わる自然文にする
- 実装手段より、利用者または保守者に起きる変化を先に書く
- タイトルと同じ文を本文に再掲しない

## 文書構成

存在する見出しは次の順で出す。並べ替えと追加をしない。

- `## 変更目的`、`## 変更内容`、1 つ以上のトピック見出し、`## テスト内容` は省かない
- `### 処理フロー`、`## レビュー観点`、`## 関連チケット`、`## 関連 Issue` は、各節の省略条件に従う

```markdown
## 変更目的

- [変更目的]

## 変更内容

- [冒頭]

### 処理フロー

[処理フロー]

### [トピック見出し]

- [トピック]

## レビュー観点

- [レビュー観点]

## テスト内容

### 自動テスト

- [自動テスト]

### 動作確認

- [動作確認]

## 関連チケット

[関連チケット]

## 関連 Issue

[関連 Issue]
```

### 変更目的

なぜこの変更が必要かを書く。

- 他のスキルから呼ばれたときは、そのスキルが定める情報収集と質問の条件を優先する
- Issue、会話、コミットメッセージの本文と件名から取る。同じ優先度の情報が複数あるときは、課題や判断理由を詳しく説明しているものを優先する
- 情報が食い違うときは、現在の会話での明示的な訂正、対象 MR に紐づく Issue、新しいコミットメッセージの順に優先する。この順でも解消できなければユーザーに聞く
- diff から推測しない
- 課題と、それをどう解決する方針かまで書く。情報源に課題が無く変更方針しかない場合は、理由を補わず確認できる方針だけを書く
- 対話中で、課題も変更方針も情報源から分からなければユーザーに聞く
- `## 変更内容` の列挙にしない

### 変更内容

差分で何がどう変わったかを書く。

#### 冒頭

変更の全体像を、`## 変更内容` の直下に見出しなしで書く。

```markdown
- [何を変えたか]
```

- 冒頭に書いた点をトピック見出しで詳述してよい
- 冒頭は変更全体を 1〜2 項目でまとめ、個々のトピックを列挙しない
- トピック見出しの言い換えだけにしない

#### 処理フロー

レビュアーが変更の全体像をつかめるように、コンポーネント間のやり取りの順を図示する。

- 変更された振る舞いが複数のコンポーネントにまたがり、その順序、分岐、状態遷移の理解に図が役立つときだけ、図を 1 つ書く
- 同型の流れが複数のモジュールに並ぶときは、代表する 1 つを実ファイル名で描き、対応するモジュールのファイル名は補足に挙げる
- 代表は、変更された分岐や制約を最も多く含み、変更目的を説明しやすいモジュールにする。差が無ければどれを選んでもよい
- コンポーネント間のやり取りが主ならシーケンス図、分岐や状態遷移が主ならフローチャートにする
- コンポーネントは、変更の判断を担うファイル、外部サービス、プロセス外に状態が残る永続ストアを単位にする
- 外部サービスや永続ストアへ値を受け渡すだけの薄いファイルは、接続先へ畳む。分岐、変換、キャッシュ有効性など変更の主題となる判断を持つファイルは独立させる
- ファイルはリポジトリルートからの実ファイルパスで示す。外部サービスと永続ストアは、必要なら API、namespace、テーブル名を添えて識別できる名前にする
- 主要な経路だけ描く。分岐は変更の主題であるものだけ描き、例外やエラー処理は描かず補足に書く
- 複数ファイルの変更でも、実行順、分岐、状態遷移が無いドキュメント、設定、rename、テストだけの変更では見出しごと省く
- 差分が 1 ファイル内で閉じ、外部サービスも跨がない場合も見出しごと省く

#### トピック見出し

差分をテーマごとに書く。1 つ以上置く。

```markdown
### [トピック見出し]

[そのトピックで何がどう変わったか]

[関連コード]
```

- `[トピック見出し]` は、その節の変化。diff から付ける
- `[そのトピックで何がどう変わったか]` は、そのテーマの差分
- `[関連コード]` は、そのトピックの振る舞いを決める主要な実装。1 箇所以上。import、export、型の追従だけの変更は省く
- 同じ変更が複数のモジュールに並ぶときは、モジュールごとに分けず 1 つの見出しにまとめる。関連コードも代表する 1 モジュールだけにし、対応するモジュールは文中に挙げる
- 同型モジュールから共用する処理そのものを変更したファイルは、代表モジュールとは別に関連コードへ挙げてよい
- rename や移動が主題のときは、新しい責務の置き場所を代表する宣言を挙げる。再公開だけを行う薄い入口は省く
- 挙げる範囲は、変更を含む関数や型の宣言から終端までにする
- 関数が長く変更がその一部に限られるときは、変更を含むブロックの範囲にする
- 同じファイル内で離れた変更は、間に無関係な行が多ければ範囲を分ける
- 指す版は head の最新コミットにする。単一コミットを説明するときは、そのコミットにする

### レビュー観点

レビュアーに重点的に見てほしい箇所を書く。

```markdown
- [レビュー観点]
```

- 変更した本人しか持っていない判断を、情報源に明示された範囲だけで書く。検討して採らなかった選択肢、外部サービスの制約、意図的に扱わなかったケースなどが該当する
- 情報源は Issue、コミットメッセージ本文、会話、コード中のコメント、diff に含まれるドキュメントに限る。diff の実装やテストから意図、理由、新しい仕様判断を導いて書かない
- 差分に無い仕組み（TTL、上限、リトライなど）を採らなかったことは、情報源にその判断が書かれているときだけ書く
- レビュアーに判断を求める点に絞る。多くても 3 点、1 点 1 行で書く
- `## 変更目的` と `## 変更内容` に書いた事実を繰り返さない
- 同じ事柄でも、変更内容には結果、レビュー観点には判断の理由を書く。理由を書くために必要な範囲で結果に短く言及してよい
- 書くことが無ければ、見出しごと省く

### テスト内容

何をテストコードで担保し、何を動かして確かめたかを分けて書く。

````markdown
### 自動テスト

- [自動テスト]

### 動作確認

- [動作確認]
````

- 自動テストは、diff にあるテストの追加・変更から何を検証したかを書く
- モック、フィクスチャ、セットアップなどテストの足場の変更は、それ自体が検証対象でなければ `## 変更内容` に書く。自動テストには、その足場を使って保証する振る舞いを書く
- 動作確認は、実際に動かして確かめたことだけ書く
- どちらも見出しを省かない。書くことが無ければ `- 特になし` とだけ書き、動かしていない理由は添えない
- 関連コードは書かない

### 関連チケット

この MR に対応する、GitLab の外にあるチケットを書く。

```markdown
https://www.notion.so/workspace/Page-Title-1a2b3c4d5e6f7890abcdef1234567890
```

- URL が分かれば URL、分からなければチケット ID を書く
- Notion のようにチケット ID を持たないシステムでは URL を書く
- ID の形式は利用するチケット管理システムに従う
- プレーンテキストで置く。バッククォート、コードブロック、引用には入れない
- チケットが分からないときはユーザーに聞かず、見出しごと省く

### 関連 Issue

この MR と Issue の関係を、本文の末尾に書く。

```markdown
Closes #10
```

- プレーンテキストで置く。バッククォート、コードブロック、引用には入れない
- `Closes` はこの MR で完了する Issue。デフォルトブランチへのマージで GitLab が閉じる
- Issue 番号が分からないときはユーザーに聞かず、見出しごと省く
