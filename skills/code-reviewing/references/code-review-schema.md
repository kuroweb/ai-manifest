# コードレビュー結果の型

## 文書構成

存在する見出しは次の順で出す。並べ替えと追加をしない。

全見出しを必ず出す。値がない場合も見出しは省略しない。指摘がない重要度セクションは `なし` と明記する。

```markdown
## レビュー判定

[レビュー判定]

## 総評

[総評]

## 指摘事項

### Critical

[Critical]

### Warning

[Warning]

### Info

[Info]

## 残留リスク

[残留リスク]
```

### レビュー判定

判定は次のいずれかにする。

- `Critical` または `Warning` がある: `修正依頼`
- `Info` のみ、または指摘なし: `承認`
- diff 不足や仕様不明で判断できない: `要確認`

diff が途中で切れている、または内容を確認できない箇所がある場合は `承認` にしない。

### 総評

変更目的との整合、主要な評価、判定理由を簡潔に書く。

### 指摘事項

重要度は `Critical`、`Warning`、`Info` の順に置く。指摘が無い重要度は `なし` とする。

指摘があるときは、重要度名を見出しに付け、次の項目で書く。

```markdown
#### [Warning] 指摘タイトル

- ファイル: app/models/example.rb:42
- 問題: 何が問題か
- 理由: なぜ問題か
- 修正案: どう直すべきか
- 補足調査: 追加調査が必要な場合のみ（なければ省略）
```

- `ファイル` は、指摘の対象
- `問題` は、何が問題か
- `理由` は、なぜ問題か
- `修正案` は、どう直すべきか
- `補足調査` は、追加調査が必要な場合のみ書く。なければ項目ごと省略する

#### 指摘基準

- `Critical`: セキュリティ事故、データ破壊、重大障害につながり得る問題
- `Warning`: 不具合、仕様逸脱、保守性、性能、テスト、セキュリティに関する実質的な問題
- `Info`: 承認を妨げない改善提案や軽微な規約違反

### 残留リスク

残るリスクが無ければ `なし` と書く。見出しは省かない。
