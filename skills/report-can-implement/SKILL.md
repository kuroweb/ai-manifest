# report-can-implement

## できること

- やりたいことが、変更を含めてこのコードベースで実装できるかを調査する
- `実装可` / `条件付きで実装可` / `実装不可` / `要確認` を判定する
- 既存例と必要な変更をレポートに出す
- 結果を日本語 Markdown として `report-can-implement.md` に保存する

## いつ使うか

- 実現できるか調べて
- 実装可能か
- これ今のコードでできる？
- 実現可能性をレポートして

## 手順

### Step 1: やりたいことを確認する

やりたいことは必須。調査の前にヒアリングする。確認した内容はレポートの `## 調査目的` にし、`# {タイトル}` はその端的な表現にする。

「何をやりたいか」を短く書いてもらう。設計メモやチケットの貼り付けでもよい。

調査目的が曖昧なまま調査に入らない。

### Step 2: コードベースを調査する

レポートを書く前に、既存コードを一次情報として調査する。調査するまでレポートは生成しない。

- 同じことを既にやっている箇所、近くの拡張点、制約になる設計を探す
- 関連コードに使えるパスと行番号、判定に効く根拠を残す
- 見つからないことは「ない」と断定せず、見つからなかったと書く
- 必要に応じて `AGENTS.md`、周辺コード、既存テスト、設計資料を読む
- 対象リポジトリのローカル規約を優先する

やりたいこととコードが矛盾した場合は、自動解決せず確認する。

### Step 3: 結果を組み立てる

このステップの前に `references/schema.md` でレポートの型を確認する。書き方は `report-patterns` に従う。

### Step 4: 可読性を確認する

保存する前に `report-patterns` を読み、Step 3 の本文がその書き方で読みやすくできるか確認する。できる箇所があれば、調査結果と節の順は変えずに直す。

### Step 5: 保存して返す

Step 4 を経た本文をワークスペースルートの `report-can-implement.md` に書き出す。

既存の `report-can-implement.md` があれば上書きする。保存後、保存先パスと本文をチャットへ 1 回だけ返す。

## 禁止事項

- `references/schema.md` を読まずに出力しないこと
- `report-patterns` を読まずに可読性を確認しないこと
- コードを調査する前にレポートを生成しないこと
- 調査していない事実を断定しないこと
- 見つからないことを「存在しない」と言い切らないこと
- ヒアリングしていないやりたいことを推測で埋めないこと
- 実装可否の判断に不要な実装や PoC コードを書かないこと
