# GitHub Issueの型

Issueの種類に対応する形式を一つ選ぶ。見出しの順序を変えず、内容が無い見出しを残さない。

## タイトル

```text
<対象>: <内容>
```

- 対象には、機能、画面、API、モジュールなど、影響範囲を表す具体的な名前を書く
- 内容には、問題または必要な変更を簡潔に書く
- 72文字以内を目安にする

## 開発タスク

利用者から見た振る舞いを変えない開発作業に使う。リファクタリング、依存の更新、CI、インフラなど。

Issue type: `Task`

```markdown
## 目的

## 背景

## 受け入れ条件

- [ ] [検証可能な完了条件]

## 対象外
```

### 目的

この作業で何を達成するかを書く。

```markdown
[達成すること]。
```

- 完了したかを判断できる状態で書く
- 対象の名前や変更内容はタイトルに任せ、繰り返さない
- 悪い例: `保守性を高める。`

### 背景

目的がなぜ必要になったかを、確かめられる根拠と一緒に書く。

```markdown
- [経緯]（[根拠]）
```

- `[根拠]` は Issue や PR のリンク、期限の日付、計測値、報告者など
- 根拠を示せないときは、起票前に目的を確かめる
- 悪い例: `- 技術的負債が溜まっている`

### 受け入れ条件

目的を達成したと判断できる条件を書く。

```markdown
- [ ] [完了後の状態]
```

- 目的が複数の状態を含むときは、状態ごとに一項目にする
- 目的に無い条件を足さない
- 完了後のコード、設定、挙動の状態は書いてよい。作業手順は書かない
- 悪い例: `- [ ] [対象]が改善されている`

### 対象外

この開発タスクで扱わないことを書く。

```markdown
- [今回扱わないもの]
```

- 別のIssueで扱うときは、そのIssueを添える
- 書く内容が無ければ見出しごと省く

## 機能追加

利用者から見た振る舞いを追加または変更するときに使う。

Issue type: `Feature`

```markdown
## 概要

## 背景

## 期待する振る舞い

## 受け入れ条件

- [ ] [検証可能な完了条件]
```

### 概要

何を追加または変更するかを書く。

```markdown
[利用者]が[対象]で[できるようになること]。
```

- `[対象]` は機能、画面、API、コマンドなどの具体的な名前
- `[できるようになること]` は利用者から見た結果
- 悪い例: `[対象]を便利にする。`

### 背景

今できないことと、それで何が困るかを、確認できる事実で書く。

```markdown
- [今できないこと、または今の制約]
  - [それで困ること]
```

- `[今できないこと、または今の制約]` には対象の名前、今の挙動、件数や頻度などの数値を使う
- `[それで困ること]` は誰が、いつ、何に困るかを書く
- 問題が複数あるときは、問題ごとに一項目にする
- 概要や受け入れ条件を繰り返さない
- 悪い例: `- [対象]の使い勝手が悪い`

### 期待する振る舞い

利用者から見た振る舞いと制約を書く。

```markdown
- [条件や操作]のとき、[振る舞い]
- 制約: [守るべき制約]
```

- `[振る舞い]` は利用者が観測できる結果で書く
- `制約:` は入力の上限、権限、既存の振る舞いとの両立など、守るべきものがあるときだけ書く
- 内部設計、ライブラリ、実装手順は書かない
- 悪い例: `- [対象]がいい感じに動く`

### 受け入れ条件

期待する振る舞いごとに、満たしたと判断できる条件を書く。

```markdown
- [ ] [条件や操作]のとき、[確認できる結果]
```

- 各項目は、期待する振る舞いのどれに対応するかが分かるように書く
- 期待する振る舞いに無い条件を足さない
- 一項目には一つの条件だけを書く
- 悪い例: `- [ ] [対象]が使えるようになっている`

## バグ修正

期待する振る舞いと実際の振る舞いが食い違うときに使う。

Issue type: `Bug`

```markdown
## 概要

## 再現手順

1. [操作]

## 期待する結果

## 実際の結果

## 環境

- バージョン: [ある場合]

## 受け入れ条件

- [ ] [検証可能な完了条件]
```

### 概要

どのような不具合が起きるかを書く。

```markdown
[対象]で[操作や条件]のとき、[起きる不具合]。
```

- `[対象]` は機能、画面、API、コマンドなどの具体的な名前
- 再現手順、原因の推測、修正方法は書かない
- 悪い例: `[対象]が正しく動かない。`

### 再現手順

不具合を再現するために必要な操作を順番に書く。

```markdown
1. [操作]
2. [操作]
```

- 一手順には一つの操作だけを書く
- 前提となるデータや設定があれば、最初の手順に書く
- 会話や確認済みの事実から分からない手順を推測しない

### 期待する結果

同じ操作で本来どうなるべきかを書く。

```markdown
[観測できる結果]
```

- 実際の結果と同じ粒度で書き、比べられるようにする
- 悪い例: `正しく動く`

### 実際の結果

実際に起きる挙動を書く。

````markdown
[観測できる結果]

```text
[エラーメッセージやログ]
```
````

- 期待する結果と同じ粒度で書く
- エラーやログは、省略や言い換えをせず必要な範囲で添える。無ければコードブロックごと省く

### 環境

再現性に関係する情報だけを書く。

```markdown
- [項目]: [値]
```

- `[項目]` はバージョン、OS、ブラウザ、実行環境など、再現性に関係するものだけ
- 書く内容が無ければ見出しごと省く

### 受け入れ条件

修正後に確認できる結果を書く。

```markdown
- [ ] [再現手順の操作や条件]のとき、[確認できる結果]
```

- 期待する結果を確認する条件を含める
- 同じ原因で起きうる別の操作や条件があれば、それも一項目ずつ書く
- 実装方法は書かない
- 悪い例: `- [ ] 不具合が直っている`
